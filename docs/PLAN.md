# NexusRank — Build Plan

Each phase ends with a **gate**: `npm run typecheck && npm run lint && npm test && npm run build` must all pass, and the phase must meet its acceptance criteria. Don't start the next phase until the current one passes its gate.

---

## Phase 0 — Scaffold & tooling

- [x] Vite + React + TypeScript (strict), with multi-entry builds for popup, dashboard, background and content
- [x] Hand-rolled Vite multi-entry build chosen over `@crxjs/vite-plugin` (reason in docs/DEVELOPER.md)
- [x] Bootstrap 5 (bundled), lucide-react, jsPDF, Vitest + happy-dom, Playwright (installed; e2e config comes in Phase 13)
- [x] ESLint and Prettier
- [x] `manifest.json` (MV3) with `activeTab`, `scripting` and `storage`, plus icons in 16/32/48/128 px
- [x] Copy the spec into `docs/SPEC.md`, and create empty `PERMISSIONS.md`, `LIMITATIONS.md` and `DEVELOPER.md`

**Accept:** `npm run build` produces `dist/`, which loads with Load unpacked without errors. The popup opens and shows "NexusRank".

## Phase 1 — Types & messaging skeleton

- [x] `types/snapshot.ts` (`PageSnapshot`), `types/check.ts` (`CheckResult`, `Status`, `Severity`, `Category`) and `types/report.ts` (`AuditReport`)
- [x] Background flow: popup → "Analyze" → `chrome.scripting.executeScript({files:[content.js]})` on the active tab → snapshot returned
- [x] Handle restricted pages (`chrome://`, the Web Store, `file://` without permission, PDFs) with a clear error state
- [x] A loading state, an error state and a retry (Re-analyze button)

**Accept:** Clicking Analyze on any normal site logs a real snapshot. On `chrome://extensions` the popup shows a friendly "can't analyze this page" message.

## Phase 2 — DOM extraction

Build out the extractor so it captures:

- head: title, all meta tags, canonical(s), robots, viewport, `lang`, hreflang, OG and Twitter tags, `<link>` elements
- headings (level, text, order, empty flag), paragraphs (text, word count), lists, tables, `<details>`/FAQ-like blocks
- images (src, alt present/empty, width/height attributes, natural size, `loading`, filename)
- links (href, resolved URL, internal/external, rel tokens, anchor text, same-page `#`, invalid schemes)
- scripts, stylesheets and DOM node count; HTML size (`document.documentElement.outerHTML.length`, labelled as an approximation); `performance.getEntriesByType('resource')` where available
- structured data: raw JSON-LD blocks (with parse errors kept), Microdata items, RDFa (`typeof`/`property`)
- author, date and `<time>` signals; `address`, `tel:` and `mailto:` links
- robots.txt and sitemap: same-origin fetch with a timeout; record the status as `found`, `not_found` or `inaccessible` (these are different statuses)

**Accept:** Unit tests run the extractor against `tests/fixtures/*.html` (happy-dom) and assert the snapshot fields. The snapshot is JSON-serializable and stays under 5 MB on the very-large fixture, because text is truncated with a flag.

## Phase 3 — Test fixtures

Create these fixtures in `tests/fixtures/`: `well-optimized`, `missing-metadata`, `multiple-h1`, `missing-alt`, `bad-jsonld`, `faq`, `article`, `organization`, `empty` and `very-large` (generated by a script). Each fixture has an `expected.json` that lists the key check IDs and their expected statuses.

## Phase 4 — SEO analyzers (pure)

- [x] `seo/metadata`, `seo/headings`, `seo/images`, `links/links`, `seo/technical`, `seo/performance`
- [x] Each check has a stable ID, for example `seo.title.length` or `tech.canonical.conflict`
- [x] Thresholds come from `scoring/config.ts`
- [x] Unit tests cover the pass, warn, fail and not-applicable paths for **every** check

**Accept:** Every fixture produces the statuses listed in its `expected.json`.

## Phase 5 — AEO analyzers

Cover question detection (a `?` at the end, plus who/what/why/how/can/does openers in headings and paragraphs), the distance between a question and the paragraph that answers it, FAQ sections, FAQPage schema, definition patterns ("X is a…"), direct-answer paragraphs (40–60 words right after a heading), lists, tables and steps, paragraph length, and a readability indicator (Flesch for English only; `not_tested` for other languages). Also cover author, dates, citations (outbound links in `<cite>`/`<blockquote>` or reference sections) and conversational coverage.

Every finding includes the actual text as evidence. Copy must never imply guaranteed selection by an answer engine.

## Phase 6 — GEO analyzers

Cover Organization, Person and Product/Service entities (from schema plus on-page signals), `sameAs`, brand consistency (site name vs. OG site name vs. schema name vs. title suffix), contact information, authorship and expertise, topical coverage (heading term clusters), internal contextual links, and factual-claim and reference indicators.

Each result is tagged `evidence: detected` or `inferred`. Copy must never claim to measure AI citations.

## Phase 7 — Schema inspector

- [x] Normalize JSON-LD, Microdata and RDFa into one tree, handling `@graph`, arrays and nesting
- [x] Per-type property maps (`schema/types/*.ts`) for Organization, LocalBusiness, Person, Article, Product, Service, FAQPage, BreadcrumbList, WebSite and WebPage, split into `required` (kept minimal), `recommended` and `optional`
- [x] Report invalid JSON-LD with its error message and the block index

**Accept:** On the bad-jsonld fixture, the inspector reports a syntax error without crashing and still parses the valid blocks.

## Phase 8 — Scoring engine

- [x] `score(category) = Σ(weight × statusValue) / Σ(weight)` over applicable checks, where passed = 1, warning = 0.5 and failed = 0
- [x] Overall score = Technical 35% + On-page 25% + AEO 20% + GEO 20%, re-normalized if a category has no applicable checks
- [x] Severity multipliers are configurable
- [x] Expose a breakdown object so the UI can show exactly how each score was computed

**Accept:** Unit tests cover every weighting rule, all-N/A categories and rounding.

## Phase 9 — Storage & history

- [x] `chrome.storage.local` wrapper with versioned schema, a configurable history cap (default 50) and delete/clear actions
- [x] Store reports only, not full page HTML. Use the `unlimitedStorage` permission only if it's justified.

## Phase 10 — Popup UI

URL and score summary, the four category scores, the top 3 issues, plus Analyze, Re-analyze and Open dashboard buttons.

## Phase 11 — Dashboard UI

Sections: Overview, Technical SEO, On-page, AEO Intelligence, GEO Intelligence, Schema Inspector, Content Structure (heading tree), Links, History, Compare and Reports.

- Dark navy/charcoal theme with blue and purple accents, built from Bootstrap plus CSS variables
- Filters by status, severity and category; expandable evidence
- SERP snippet preview, metadata preview, a JSON viewer, and score charts drawn in SVG with no chart library
- Compare: pick two saved reports and view a side-by-side diff of scores, checks and key metadata

## Phase 12 — Exports

PDF (jsPDF, multi-page, with the limitations disclaimer), CSV (one row per check, properly escaped) and JSON (the full `AuditReport`). Downloads use Blob URLs, so no `downloads` permission is needed.

## Phase 13 — E2E tests

Playwright with `launchPersistentContext` and `--load-extension=dist`. Serve the fixtures from a local server. Test these flows: popup analyze, open dashboard, filters, history, compare, and each export. Fail the run on any console error.

## Phase 14 — Hardening & docs

- [x] Audit for no remote URLs: `grep -r "http" dist/` must show only inert string literals (XML namespaces, a React error-doc pointer); enforced by `npm run audit:dist`
- [x] Fill in `README.md` (install, build, test), `docs/DEVELOPER.md` (how to add a check), `docs/PERMISSIONS.md` and `docs/LIMITATIONS.md`
- [x] Produce a final production build and a zip ready for the Chrome Web Store

## Watch-outs

- **Dashboard tab vs. analyzed tab:** opening the dashboard changes the active tab, so pass `tabId` explicitly.
- **robots.txt:** fetch it from the content script, where it's same-origin and needs no host permission. If you fetch it from the background script instead, you'll need host permission.
- **SPAs:** the extractor reads the DOM at the time you click, which is a known limitation. Re-analyze picks up later changes.
- **iframes and shadow DOM:** not analyzed in v1. Document this as a limitation.
- **Performance API:** cross-origin resources don't report their size unless the server sends `Timing-Allow-Origin`. Mark those as inaccessible, not as zero.
